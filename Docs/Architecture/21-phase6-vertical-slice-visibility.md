> **Created**: 2026-05-25

> **Runtime core**: FROZEN (`v0.5.0-stabilized`)
>
> This document defines the SECOND implementation slice for Phase 6.
> Visibility replication validates that the semantic-event pattern
> (provenance → suppression → replay → observability) generalizes
> from rename to a different editor mutation.

---

## 1. Purpose

This vertical slice exists to validate that the semantic-event
architectural pattern established by the rename slice generalizes to
a second, different editor mutation:

| Foundation | Visibility Validation |
|-----------|----------------------|
| **Provenance tracking** | Visibility is a different mutation type (bool toggle vs string rename). Does provenance flow identically? |
| **Suppression systems** | No callback risk for visibility (unlike rename's `OnActorLabelChanged`). Does the RAII suppression pattern still make sense without recursion risk? |
| **Reconnect replay semantics** | Visibility state (hidden/visible) is trivially idempotent — setting it twice produces the same result. Simplifies replay verification. |
| **Fixed-length packet handling** | Visibility is 29 bytes fixed per object (vs rename's variable-length strings). Validates the separate-block parser pattern against a simpler wire format. |
| **Observability model** | `[VISIBILITY]` log prefix, separate counters, separate TRACE_CPUPROFILER_EVENT_SCOPE names. Do they compose correctly alongside rename telemetry? |

### Why Visibility and Not Hierarchy

Visibility was chosen over hierarchy as the second slice because:

| Criterion | Visibility | Hierarchy |
|-----------|------------|-----------|
| Packet complexity | Fixed 29 bytes per object | Variable-length (parent GUID, slot info) |
| Suppression complexity | No callback recursion risk | Parent re-attach may fire `OnAttachmentChanged` |
| Replay complexity | Idempotent bool compare | Parent resolution order-dependent |
| Blender API | Single call: `obj.hide_set()` | Recursive: parent must exist before child |
| Rollback cost | Low — trivially revertible | High — parent-child state coupling |

## 2. Packet Semantics

### Packet Type

```
PT_Visibility = 0x0B
```

Assigned from the available type space (between PT_EndSnapshot `0x0A`
and PT_Rename `0x0C`).

### Wire Format (per object, fixed 29 bytes)

```
Offset  Size  Field           Description
------  ----  -----           -----------
 0       16   GUID            FGuid (4 × uint32 LE, same as all other packets)
16        1   bHidden         0 = visible, 1 = hidden in editor (uint8)
17        4   Sequence        Monotonic per-GUID sequence number (uint32 LE)
21        8   Timestamp       Monotonic timestamp (double LE)
```

Each visibility packet may contain multiple visibility objects batched
together. The `ObjectCount` field in the 24-byte header specifies how
many visibility records follow.

### Discrete Semantic Event

Visibility replication is a **discrete semantic editor event**, NOT a
state stream. Each packet represents a single user action (hide or
unhide), not a continuous state sample.

| Property | Visibility Replication | Transform Replication |
|----------|----------------------|----------------------|
| **Nature** | Discrete semantic event | Continuous state stream |
| **Frequency** | Low (user-initiated, bursty) | High (60 Hz typical) |
| **Semantics** | Toggle-sensitive: hide→unhide→hide matters | Overwrite-oriented: latest state wins |
| **Interpolation** | Not applicable | Friendly — missing frames interpolated |
| **Provenance required** | Yes (reuse EChangeOrigin) | No |
| **Suppression required** | Yes (pattern adherence) | No |
| **Replay sensitivity** | Must deduplicate, reject stale | Low — overwrite with latest |

### Batch Processing

Multiple visibility objects in a single packet are processed
sequentially within the PT_Visibility case branch. If any object
fails validation (truncated, malformed), the entire packet is
rejected and `Stats.MalformedPackets` incremented (same pattern as
PT_AssetDef and PT_Rename).

## 3. Replay Semantics

### Per-GUID Monotonic Sequence

Each visibility toggle carries a monotonic per-GUID sequence number
(uint32), generated by the Blender sender. The UE receiver maintains
`FVisibilitySequenceTracker`:

```cpp
struct FVisibilitySequenceTracker
{
    TMap<FGuid, uint32> LastSequence;
    static constexpr uint32 MAX_TRACKED_GUIDS = 2048;

    bool IsStaleOrDuplicate(const FGuid& Guid, uint32 IncomingSeq)
    {
        if (const uint32* LastSeq = LastSequence.Find(Guid))
            return IncomingSeq <= *LastSeq;
        return false;
    }

    void Update(const FGuid& Guid, uint32 AppliedSeq)
    {
        if (LastSequence.Num() >= MAX_TRACKED_GUIDS)
            LastSequence.Remove(LastSequence.CreateIterator().Key());
        LastSequence.Add(Guid, AppliedSeq);
    }
};
```

### Stale Rejection Rules

- `IncomingSeq <= LastSeq` → stale or duplicate → reject with Warning log + `Stats.VisibilityStaleRejections++`
- `IncomingSeq > LastSeq` → accept → apply + update tracker

### Reconnect Replay

1. `PT_BeginSnapshot` → sets `bInSnapshotBuild = true`
2. Visibility events sent during snapshot → tag as `EChangeOrigin::Replay`
3. `PT_EndSnapshot` → sets `bInSnapshotBuild = false`

Replayed visibility events:
- Check `FVisibilitySequenceTracker` for stale/duplicate
- Check `FindActorFast(Guid)` — reject if actor not found
- Apply `SetIsTemporarilyHiddenInEditor(bHidden)` with `FScopedVisibilitySuppression` + `FScopedChangeOrigin(Replay)`
- Update `FVisibilitySequenceTracker`

### Idempotency

`AActor::SetIsTemporarilyHiddenInEditor(bool)` is naturally idempotent:
applying the same hidden state twice produces the same visual result.
The sequence tracker prevents double-application, but even without it,
no corruption would occur.

## 4. Provenance Rules

Reuse the existing `EChangeOrigin` enum (defined in `SyncTypes.h`,
in-memory only, never on the wire):

| Origin | When Set | Behavior |
|--------|----------|----------|
| `RemoteReplicated` | Normal packet processing (default) | Apply, increment `Stats.VisibilityProcessed`, log origin |
| `Replay` | When `bInSnapshotBuild == true` | Apply, increment `Stats.VisibilityReplayApplied`, log origin |
| `LocalUser` | Future UE→Blender direction | Not wired in this slice |
| `Recovery` | Future actor recovery path | Not wired in this slice |

### Provenance Propagation

```
Blender sync.py detects hide_get() change
  → no provenance tag (Blender-side concept)
  → serialize PT_Visibility
  → TCP send

UE ProcessBinaryPacket receives PT_Visibility
  → bInSnapshotBuild ?
      → Yes: Origin = EChangeOrigin::Replay
      → No:  Origin = EChangeOrigin::RemoteReplicated
  → HandleVisibility(Guid, bHidden, Seq, Ts, Origin)

HandleVisibility
  → FScopedChangeOrigin OriginScope(Origin)  // set thread-local
  → FScopedVisibilitySuppression Suppress(Guid)  // RAII guard
  → Actor->SetIsTemporarilyHiddenInEditor(bHidden)
  → FVisibilitySequenceTracker.Update(Guid, Seq)
  → Stats updated
  → [scope exit] OriginScope restores previous provenance
  → [scope exit] Suppression logs exit
```

## 5. Suppression Strategy

### FScopedVisibilitySuppression

Same pattern as `FScopedRenameSuppression` — RAII guard that wraps the
visibility apply call:

```cpp
struct FScopedVisibilitySuppression
{
    FString GuidStr;
    FScopedVisibilitySuppression(const FGuid& InGuid)
        : GuidStr(InGuid.ToString(EGuidFormats::Digits))
    {
        UE_LOG(LogLiveSync, Verbose,
            TEXT("[VISIBILITY] Enter suppression scope (GUID=%s)"),
            *GuidStr);
    }
    ~FScopedVisibilitySuppression()
    {
        UE_LOG(LogLiveSync, Verbose,
            TEXT("[VISIBILITY] Exit suppression scope (GUID=%s)"),
            *GuidStr);
    }
};
```

### Why Suppression When There's No Callback?

The suppression scope serves two purposes even without a callback:

1. **Architectural consistency** — Every Phase 6 semantic event follows
   the same pattern: provenance scope + suppression scope + mutation.
   This reduces cognitive load for future maintainers.
2. **Future-proofing** — If a future UE engine version adds an
   `OnActorHiddenInEditorChanged` callback, the suppression infrastructure
   is already in place. No emergency refactor needed.

### Suppression Properties

| Property | Requirement |
|----------|-------------|
| Scoped | Active only within HandleVisibility call stack. RAII. |
| Temporary | Does not persist across frames. No global flags. |
| No cross-frame leakage | Stack-allocated GuidStr destroyed on scope exit. |
| Observable | Entry/exit logged at Verbose level. |
| Nested-safe | Independent instances, no shared mutable state. |

## 6. Observability Requirements

### Required Diagnostics

| Category | What to Log | Level |
|----------|-------------|-------|
| **Visibility application** | Origin, GUID, state (hidden/visible), sequence | Log |
| **Suppression scope** | Enter/exit | Verbose |
| **Stale GUID visibility** | GUID, state, current state (Tombstoned/Unknown) | Warning |
| **Stale sequence** | GUID, state, incoming seq, last seq | Warning |
| **Replay visibility** | GUID, state, seq, replay batch | Log |
| **Malformed packet** | Truncation detail | Warning |

### FLiveSyncStats Counters

| Counter | Type | When Incremented |
|---------|------|------------------|
| `VisibilityProcessed` | `std::atomic<int32>` | RemoteReplicated visibility applied |
| `VisibilityStaleRejections` | `std::atomic<int32>` | Stale/duplicate sequence rejected, or GUID not tracked |
| `VisibilityReplayApplied` | `std::atomic<int32>` | Replay-tagged visibility applied |
| `VisibilityReplaySkipped` | `std::atomic<int32>` | Replay-stale visibility rejected |

### TRACE_CPUPROFILER_EVENT_SCOPE

| Scope Name | Location |
|------------|----------|
| `UELiveSync_HandleVisibility` | HandleVisibility function entry (after CHECK_GAME_THREAD) |
| `UELiveSync_ProcessVisibilityPackets` | PT_Visibility parse block entry |

### Log Prefix

All visibility-related logs use `[VISIBILITY]` prefix for easy grep:

```

[Warning] [VISIBILITY] Rejected — no tracked actor for GUID=...
[Warning] [VISIBILITY] Rejected — stale/duplicate sequence ...
```

## 7. Architectural Constraints

### Preserved Invariants

| System | Constraint | How Visibility Preserves It |
|--------|------------|----------------------------|
| Transform packet layout | 81 bytes per V4+ object | Visibility uses separate PT_Visibility branch, never enters transform loop |
| Tick pipeline ordering | ProcessQueuedPackets → InterpolateTransforms → ResolvePendingAttachments → RecoverMissingActors → ResolvePendingAssets | Visibility inlined into ProcessQueuedPackets via PT_Visibility case branch, no reordering |
| Queue ownership | LiveSyncQueue bounded MPSC (128), network thread enqueues | Visibility packets enqueued by network thread as FLiveSyncPacket, same as all other types |
| Network thread ownership | Owns Recv(), parse, enqueue only | No changes — network thread deserializes header + type dispatch only |
| Parser invariants | Separate case branches, per-object bounds checks, return on malformed | PT_Visibility follows PT_AssetDef/PT_Rename pattern: separate block, fixed-size per-object loop, return on truncation |
| Reconnect lifecycle | StopNetworkThread clears state, BeginSnapshot→replay→EndSnapshot | Visibility state cleared in StopNetworkThread + ConsoleReset; replay during bInSnapshotBuild |
| FSyncTransformState | POD-only, no FString fields, no name/storage fields | Visibility state lives in separate TMap<FGuid, bool> |
| FNV checksum | Updated for each packet type | Update H = fnv(H, 0x0B) |

### Prohibited Actions

| Action | Why |
|--------|-----|
| Reuse transform interpolation path | Interpolation assumes continuous numeric state. Visibility is discrete bool. |
| Reuse rename sequence tracker | Separate semantic lane requires separate tracker for independent replay state. |
| Mix visibility objects into main transform loop | Visibility has different wire format (29 bytes fixed vs 81 bytes). Must remain in separate branch. |
| Add fields to FSyncTransformState | Visibility state is not transform state. Lives in TMap<FGuid, bool>. |
| Access visibility state from network thread | All UObject/actor mutation on game thread only. |
| Skip provenance tagging | Every visibility mutation must carry EChangeOrigin. |

## 9. Rollback Criteria

### Immediate Pause Conditions

| Condition | Why | Action |
|-----------|-----|--------|
| Visibility implementation requires modifying parser version dispatch or header parsing | Parser is FROZEN | Pause → ADR review |
| Visibility implementation requires changing Tick pipeline ordering | Pipeline is FROZEN | Pause → ADR review |
| Visibility implementation requires modifying LiveSyncQueue, PendingAssetQueue, or LiveSyncRunnable | Queue/thread ownership is FROZEN | Pause → ADR review |
| Visibility implementation requires adding fields to FSyncTransformState | Object layout is FROZEN | Pause → ADR review → Use separate TMap |
| Visibility implementation uses transform interpolation logic | Interpolation is for state streams, not semantic events | Pause → ADR review |

### Rollback Sequence

1. Revert the offending change
2. Log an ADR describing the proposed frozen-zone modification
3. Evaluate alternative approaches that do not touch frozen zones
4. If no alternative exists, escalate to project lead
